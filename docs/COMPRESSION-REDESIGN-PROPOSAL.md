## 1. 数据审计：结论合规，但**原结论取样不全，已更正**

### 1.1 合规性核验（通过）

| 核验项 | 结果 |
|---|---|
| 两条独立计量路径是否一致 | ✅ 一致。`llm_calls` 表与 FileLogger 对同一 session 的 token 合计完全相同（`1e241ab4` = **209,018**；`78e68370` = **197,653**；`b44c4c8e` = **75,267**） |
| 预算拒绝是否显式记录 | ✅ 是。被拒调用在 `llm_calls` 里 `status='error'` + `error_msg='agent_gateway: token budget exhausted…'`，不是静默丢弃 |
| 压缩前后比较是否同口径 | ✅ 是（均为字符）；"有没有变化"的结论不受单位影响 |
| 是否存在未记录的失败 | ✅ 无；FileLogger 全 80 条 `status=success` |

### 1.2 🔴 更正：压缩**不是"结构性永远 0%"**

上一轮我基于 7 条压缩记录得出"真实庭审省 0.0%"。**完整日志有 12 条**，后 5 条**省 17.7–22.1%**：

| session | 任务 | 条数 | 字符（前→后） | 省幅 |
|---|---|---|---|---|
| 1e241ab4（standard） | react_think×4 / retry×3 | 1–6 → 同 | 20,742–22,923 → **不变** | **0.0%** ×7 |
| 78e68370（quick） | react_think×3 / retry×2 | 3→3 / 5→5 / 6→5 / 9→5 / 10→6 | 25,467–28,267 → 20,823–22,037 | **17.7–22.1%** |

**而且省幅的来源不是"四步智能压缩策略"，而是 system 消息的兜底上限被触发**：

`msgTruncateLimits` 对 system 消息用 `compressMaxSystemMsgLen=24000` / `compressSystemTargetLen=20000`。
算术可证——每条的 `after ≈ 20000 + 保留的非 system 尾巴`：

```
25,467 -> 20,823   after-20000 = 823   （3 条非 system 全保留）
26,338 -> 21,028   …          1,028
28,159 -> 21,929   …          1,929
28,267 -> 22,037   …          2,037
```

对照：`1e241ab4` 的 system 在 **20.7–22.9k < 24,000** → 上限没触发 → **真的 0%**；
`78e68370` 的 system **> 24,000** → 触发截断到 20,000 → 才出现 18–22%。

**更正后的正确表述**：
> 压缩的省幅 =（非 system 消息被丢弃）+（system 超 24,000 字节时的兜底截断到 20,000）。
> 短/中庭审（system < 24k 且消息列表 ≤ ~5）**省 0%**；长庭审 **17–22%**，但**主要来自那条兜底上限**，
> 四步流水线只在列表 ≥ ~9 条时才开始丢消息（实测 9→5 / 10→6）。

### 1.3 仍在的一句话

**token 大头在一条永不参与"评分/原子组/贪心打包"的 system 消息里** —— 这点不变，所以：
- 只靠压缩器，省幅天花板 = 那条 system 超出 24k 的部分 + 非 system 尾巴；
- 要让"省"变得可控且不伤输出契约，得改**素材组装层**（见 §2）。

## 2. 方案：把 system 消息拆成「契约块 + 素材块」（未实施）

### 2.1 问题

`buildInitialMessages` 把三类内容混在**一条** system 消息里：

```
[契约] baseRules（输出格式 / 行为约束 / 工具协议）  ← 绝不能压（v2.10 实测：压它→销毁指令→模型编造证据）
[素材] 证据全文 · 庭审历史（按时间顺序追加在末尾）   ← 应该可压
[素材] 投影区块（对方的公开发言 / 私有笔记 / 信念）   ← 应该可压
```

结果：压缩器要么整条不动（0%），要么在**超标时从末尾截断**——而末尾正是**最新的庭审历史**（见 §3.2）。

### 2.2 方案

把 system 拆成**两条消息**：

1. `system#1 = 契约块`（baseRules + 工具协议 + 输出格式）—— 标记为**不可压**（压缩器按 role/标记跳过）；
2. `system#2 = 素材块`（证据 + 庭审历史 + 投影区块）—— **允许压缩器正常参与评分/原子组/贪心打包**，
   并按"保留最近 N 轮"的语义裁剪，而不是从末尾硬切。

好处：既守住"契约不压"（用户定的"system 压缩最低优先级"，实际落成"契约永不动"），
又让压缩真正作用到 token 大头，且裁剪语义可解释。

### 2.3 附带修（审计新发现，比主方案更该先做）

**兜底截断应从"砍尾部"改为"保最近、砍最旧"。** 现在 `cutBytesRuneSafe(Content, keep)` 取**前** N 字节，
而庭审历史是**按时间顺序追加在末尾**的 —— 于是超长时被砍掉的恰是**最新发言**（对"回应对方最新论点"
最不利）。至少应改成"保留末尾 N 字节"，或按行裁剪只丢最旧的历史行。

### 2.4 前置与验收（实施时必须）

- 属**行为变更**（改变模型所见）→ 真实庭审 **A/B 同题对跑**（对照庭审走向 + 发言质量 + 反幻觉重试率）；
- 补**注入式回归**：断言"契约块未被压缩"、"素材块按最近优先裁剪"；
- 过 AGENTS.md §11 docker 业务验证 + 浏览器实测；
- 通过后同步 PRD/tech-spec/ADR 0006 的节省率口径（届时才谈"重新定义 ≥30%"）。

## 3. 审计中发现的其他异常（5 项）

### 3.1 ⚠️ 限流疑似"自食其果"：砍 max_tokens → 截断 → 重试

`1e241ab4` 前 26 次调用**零重试**；从第 26 次起进入限流档（`throttled=true`，`max_tokens` 500 → **100–297**），
随后 7 次调用里出现 **3 次 `react_think_retry`**。

| | 正常 think | 被限流后 |
|---|---|---|
| 调用数 | 26 | 7 |
| `react_think_retry` | 0 | **3** |
| 平均输入 token | 8,479 | 重试 9,108（**高于**正常） |

机制自洽：`max_tokens=100` 很可能把 ReAct 决策 JSON 截断 → 解析失败 → 重试（每次重发 ~9.8k 输入）。
粗算：限流省下的输出额度约 `7×200 = 1.4k` token，而它疑似引发的 3 次重试约 **29k** token（占全场 14%）。
**要坐实需一次对照实验**（关掉 throttle 跑同题），此处记录为"强相关 + 机制自洽"。

### 3.2 ⚠️ 兜底截断砍掉的是"最新的庭审历史"

`buildInitialMessages` 的 system 内容顺序是 `baseRules → 工具协议 → ## 庭审历史（按时间顺序）`，
截断取前 N 字节 → **末尾（最近发言）被砍**。`78e68370` 中发生 4–5 次。
对"回应对方最新发言"这一核心任务不利（见 §2.3 的附带修）。

### 3.3 ⚠️ quick 庭审也可能顶到 197.6k

`78e68370`（二轮 quick）用 **197,653**（旧预算的 98.8%），而另一场 quick（`b44c4c8e`）只用 **75,267** ——
同模式波动 **2.6 倍**（取决于 ReAct 迭代/重试次数）。→ 固定 per-session 预算是钝器；
300k 能覆盖已观测峰值，但"按模式分档 / 收敛 ReAct 迭代上限"更本质。

### 3.4 ⚠️ 预算拒绝不进 FileLogger

`1e241ab4` 在 DB 有 **35** 行、文件日志只有 **33** 条 —— 差的正是那 2 条被拒的 `final`/`verdict`。
拒绝对 DB 可见（显式 error），但在"详细调用快照"文件里**缺席**。运维若只看文件日志会漏掉"判决被拒"。

### 3.5 ⚠️ "兜底摘要"阶段从未触发

`compression_summarized_blocks` 全为空：丢弃数始终 ≤ `SummaryInsertThreshold(5)`，故摘要从不插入。
若产品期望"长庭审靠摘要保住被丢信息"，目前**实际不成立**。

### 3.6 ℹ️ 口径提醒（不是 bug，但别误用）

`compression_before/after_length` 是**字符**且**只含 messages**；`prompt_tokens` 是 **token** 且含
**单独传的 system 参数** —— 两者比值实测 2.3–2.8，**不能用固定系数换算**。
（fixture eval 的 `chars/4` 是第三把尺子，见 §M6。）

## 4. 结论与建议顺序

1. **先做 §2.3 的附带修**（截断保最近、砍最旧）—— 改动小、直接改善长庭审的素材质量；
2. 再评估 §2.2 的 system 拆分（行为变更，需 A/B）；
3. §3.1 的限流-重试耦合建议先做**对照实验**坐实，再决定是否调整限流策略；
4. §3.4 的观测缺口（拒绝不进文件日志）可顺手补一条日志，代价极低。
