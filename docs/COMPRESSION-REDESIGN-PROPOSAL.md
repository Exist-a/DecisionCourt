## 1. 数据审计：结论合规，但**原结论取样不全，已更正**

### 1.1 合规性核验（通过）

| 核验项 | 结果 |
|---|---|
| 两条独立计量路径是否一致 | ✅ 一致。`llm_calls` 表与 FileLogger 对同一 session 的 token 合计完全相同（`1e241ab4` = **209,018**；`78e68370` = **197,653**；`b44c4c8e` = **75,267**） |
| 预算拒绝是否显式记录 | ✅ 是。被拒调用在 `llm_calls` 里 `status='error'` + `error_msg='agent_gateway: token budget exhausted…'`，不是静默丢弃 |
| 压缩前后比较是否同口径 | ✅ 是（均为字符）；"有没有变化"的结论不受单位影响 |
| 是否存在未记录的失败 | ✅ 无；FileLogger 80 条 `status=success` |

### 1.2 🔴 更正：压缩**不是"结构性永远 0%"**

上一轮基于 7 条压缩记录得出"真实庭审省 0.0%"。**完整日志有 12 条**，后 5 条**省 17.7–22.1%**：

| session | 任务 | 条数 | 字符（前→后） | 省幅 |
|---|---|---|---|---|
| 1e241ab4（standard） | react_think×4 / retry×3 | 1–6 → 同 | 20,742–22,923 → **不变** | **0.0%** ×7 |
| 78e68370（quick） | react_think×3 / retry×2 | 3→3 / 5→5 / 6→5 / 9→5 / 10→6 | 25,467–28,267 → 20,823–22,037 | **17.7–22.1%** |

**省幅的来源不是"四步智能压缩策略"，而是 system 消息的兜底上限被触发**：
`msgTruncateLimits` 对 system 用 `compressMaxSystemMsgLen=24000` / `compressSystemTargetLen=20000`。
算术可证——每条的 `after ≈ 20000 + 保留的非 system 尾巴`：

```
25,467 -> 20,823   after-20000 = 823   （3 条非 system 全保留）
26,338 -> 21,028   …          1,028
28,159 -> 21,929   …          1,929
28,267 -> 22,037   …          2,037
```

对照：`1e241ab4` 的 system 在 **20.7–22.9k < 24,000** → 上限没触发 → **真的 0%**。
流水线只在非 system 列表 ≥ ~9 条时才开始丢消息（实测 9→5 / 10→6）。

**更正后的正确表述**：
> 压缩省幅 =（非 system 消息被丢弃）+（system 超 24,000 字节时的兜底截断到 20,000）。
> 短/中庭审（system < 24k 且列表 ≤ ~5）**省 0%**；长庭审 **17–22%**，但**主要来自那条兜底上限**。

## 2. 方案：把 system 消息拆成「契约块 + 素材块」（未实施）

### 2.1 问题

`buildInitialMessages` 把三类内容混在**一条** system 消息里：

```
[契约] baseRules（输出格式 / 行为约束 / 工具协议）  ← 绝不能压（v2.10 实测：压它→销毁指令→模型编造证据）
[素材] 证据全文 · 庭审历史（按时间顺序追加在末尾）   ← 应该可压
[素材] 投影区块（对方的公开发言 / 私有笔记 / 信念）   ← 应该可压
```

结果：压缩器要么整条不动（0%），要么在**超标时从末尾截断**——而末尾正是**最新的庭审历史**（见 §3.2）。

### 2.2 方案

把 system 拆成**两条消息**：

1. `system#1 = 契约块`（baseRules + 工具协议 + 输出格式）—— 标记**不可压**（压缩器按 role/标记跳过）；
2. `system#2 = 素材块`（证据 + 庭审历史 + 投影区块）—— **允许正常参与评分/原子组/贪心打包**，
   并按"保留最近 N 轮"的语义裁剪，而不是从末尾硬切。

好处：既守住"契约不压"（用户定的"system 压缩最低优先级"，落成"契约永不动"），又让压缩作用于 token 大头。

### 2.3 附带修（审计新发现，比主方案更该先做）

**兜底截断应从"砍尾部"改为"保最近、砍最旧"**（见 §3.2）。现在 `cutBytesRuneSafe(Content, keep)` 取**前** N 字节，
而庭审历史追加在末尾 —— 超长时被砍的恰是**最新发言**。

### 2.4 前置与验收（实施时必须）

- 属**行为变更**（改变模型所见）→ 真实庭审 **A/B 同题对跑**（对照庭审走向 + 发言质量 + 重试率）；
- 补**注入式回归**：断言"契约块未被压缩"、"素材块按最近优先裁剪"；
- 过 AGENTS.md §11 docker 业务验证 + 浏览器实测；
- 通过后同步 PRD/tech-spec/ADR 0006 的节省率口径。

## 3. 异常逐项根因（已读代码定位；4 项真实 + 1 项撤回）

### 3.1 ✅ 真实 · 限流把 max_tokens 砍到 100，导致 JSON 截断 → 重试（最坏打断整轮）

**机制（`throttler.go::Apply`）**：
```go
remaining := 1.0 - bs.Ratio
scaled := int(math.Ceil(float64(base) * remaining * 2))   // base = opts.MaxTokens
if scaled < 100 { scaled = 100 }                          // throttleMinMaxTokens
```
`react_think` 申请 `MaxTokens=500`（`react_runner.go:295`）→ 实测被砍成 **297 / 247 / 196 / 147 / 100**，与公式逐点吻合。

**为什么有害**：think 的输出是一整份决策 JSON（`action` + `reasoning` + `content` + `evidence_refs`…）。
**100 token（中文 ≈60 字）几乎必然把 JSON 截断** → `json.Unmarshal` 失败（`react_runner.go:303`）→ 触发
`react_think_retry`（**同样被限流到 100**）→ 若再次解析失败 → **`return error` 直接打断这一轮**
（`react_runner.go:324`），上层走用户可见的错误恢复。

**实测相关性与成本**：`1e241ab4` 前 26 次调用**零重试**；进入限流档后 7 次调用出现 **3 次重试**。
重试平均输入 **9,108** token（> 正常 think 的 8,479，因为要重发整份 prompt + 失败输出 + 提示）。
粗算：限流省下的输出额度约 `7×200 = 1.4k`，疑似引发的重试约 **29k**（占全场 14%）—— **净负**。

**定性**：真实异常（设计意图是"省 token"，实际把预算压力转化成重试成本与整轮失败风险）。
**待做**：① 对照实验坐实（关掉 throttle 跑同题）；② 若坐实，考虑给 ReAct 决策步设 max_tokens 下限
（如 ≥300）或把 `react_think` 纳入"关键输出"豁免。

### 3.2 ✅ 真实 · 兜底截断砍掉的是"最新的庭审历史"

**机制**：`truncateOversizedMessages` → `cutBytesRuneSafe(content, keep)` 保留**头部**、丢弃**尾部**；
而 `buildInitialMessages` 的拼接顺序是 `[角色/规则/证据] → [工具协议] → [## 庭审历史]`（历史**按时间顺序追加在末尾**）。
于是 system > 24,000 字节时，被丢弃的是**最近的发言**——恰是"回应对方最新论点"最需要的部分。本日 `78e68370` 触发 4–5 次。

**定性**：真实异常（保留方向反了）。**修法**：至少改为"保留末尾 N 字节"，或按行裁剪只丢最旧的历史行（§2.3）。

### 3.3 ❌ 撤回 · "quick 庭审波动 2.6 倍"是**我自己的测试失误**，不是产品异常

原判断：`b44c4c8e` 75,267 vs `78e68370` 197,653，同模式差 2.6 倍。
**复核后撤回**：逐 session 数调用次数 —— `b44c4c8e` 只有 **15** 次调用（`react_speak_stream=4`），
`78e68370` 有 **32** 次（`react_speak_stream=7`）。原因是验证 Module B 时我在开庭陈述后**误点了「直接判决」**，
跳过了 3 轮质证 → 少了近一半发言与推理。**属取样失误。**

（唯一成立的普遍事实：预算与"跑了多少轮/多少次迭代"成正比 —— 这是显然的，且是"按模式分档"的理由，不是缺陷。）

### 3.4 ✅ 真实 · 预算拒绝**不进 FileLogger**（观测不对称）

**机制**：`gateway.go:208-227` 的拒绝分支只调用 `g.recorder.Record(...)`（写 `llm_calls` 表），
随后 **`return`，不经过 `writeFileLog`**（文件日志只在真正发起 LLM 调用后写，见 `gateway.go:346`）。

**后果**：`1e241ab4` 在 DB 有 **35** 行、文件日志只有 **33** 条 —— 差的正是那 2 条被拒的 `final`/`verdict`。
运维若只看"详细调用快照"文件，会**漏掉"判决被拒"**这一最关键事件。

**定性**：真实异常（观测缺口）。**修法**：拒绝分支也补一条文件日志（代价极低）。

### 3.5 ✅ 真实 · "兜底摘要"分支在 ReAct 路径上**不可达**（死代码）

**机制**：触发条件 `droppedCount > cfg.SummaryInsertThreshold`（默认 **5**，`prompt_compressor.go:286`）。
但 ReAct 的非 system 消息数受 `MaxIterations=4`（`orchestrator.go` 构造 runner 时）约束 —— 每轮最多追加 2 条
（assistant + user），非 system 总量 ≤ ~8；`KeepRecentForcedN=3` 又强制保留最近 3 条 →
**`droppable ≤ 5`**，而条件是 `> 5` → **永不成立**。实测 `droppedCount` 最大为 **4**。

**定性**：真实异常（阈值与迭代上限不匹配 → 死分支）。若产品期望"长庭审靠摘要保住被丢信息"，
需下调阈值，或让摘要作用于非 ReAct 路径 / 更长的历史。

### 3.6 ℹ️ 口径提醒（不是 bug，但别误用）

`compression_before/after_length` 是**字符**且**只含 messages**；`prompt_tokens` 是 **token** 且含
**单独传的 system 参数** —— 两者比值实测 2.3–2.8，**不能用固定系数换算**。
（fixture eval 的 `chars/4` 是第三把尺子，见 §M6。）

## 4. 结论与建议顺序

1. **先做 §2.3 / §3.2 的截断方向修**（保最近、砍最旧）—— 改动小、直接改善长庭审素材质量；
2. **§3.1 的限流-重试耦合**：先做对照实验坐实，再决定是否给决策步设 max_tokens 下限；
3. **§3.4 的观测缺口**：拒绝分支补一条文件日志（代价极低，可顺手做）；
4. **§3.5 的摘要死分支**：要么下调阈值让它真能触发，要么明确记录"该兜底当前不生效"；
5. 最后再评估 §2.2 的 system 拆分（行为变更，需 A/B）。
