## 🎯 核心主题

**v2.10 = 让 Token 压缩"按真实成本算、按真实证据链保、按真实质量验"**

4 个核心收益：

1. **配置不再骗人** — `IsSmartCompressionEnabled` 归位到 `isChildDefault()`；`AGENT_GATEWAY_SCORE_THRESHOLD` 从死配置变成真正参与筛选
2. **证据链不再被拆散** — `orchestrator.speak()` 把 `agent_type` + `evidence_id` 注入 `llm.Message.Metadata`，`BuildAtomicGroups` 据此把同证据的多轮引用绑成一个原子组
3. **预算单位从字符数改为 token** — 按字符类别加权（CJK 1.5 tok/char、ASCII 0.25 tok/char），中文推理不再被代码块挤掉
4. **有质量回环指标了** — `verdict_evidence_accuracy` gauge 回答"压缩有没有伤到判决质量"，而不只是"省了多少 token"

## 🆕 变更明细（按 PR 切片）

### PR-1 (P0): 配置 footgun + evidence_id 链

#### #1 `IsSmartCompressionEnabled` 归位

**文件**：`internal/agent_gateway/gateway_config.go`

```go
// before — 不走 isChildDefault()，与其余 5 个子开关行为不一致
return c.Enabled && c.SmartCompression

// after
if !c.Enabled { return false }
return c.SmartCompression || c.isChildDefault()
```

**为什么**：其余子开关（PromptCompression / TokenBudget / Throttling / Fallback / FileLogger）都在 `AGENT_GATEWAY_ENABLED=true` 且无子开关时自动开启。SmartCompression 唯一例外 —— 一旦有人把 viper 默认值改回 false，它会静默回落到 legacy 而其他子功能照常开启，故障极难定位。

#### #3a `orchestrator.speak()` Metadata 注入

**文件**：`internal/agent/orchestrator.go`

`speak()` 的 `model.Message → llm.Message` 转换此前**丢弃所有 Metadata**，导致：

- 评分器 `roleWeightFor` 拿不到 `agent_type`，judge(1.5) / clerk(1.3) 的精确权重全部退化为 assistant(1.2)
- `evidence_id` 恒为空，原子组无法识别证据链

修复：`speak()` 新增 `agentMap map[uuid.UUID]model.AgentType` 入参，5 个公开 Speak 函数透传，`service.go` 从 `agents` 构造 map。

#### #3b `BuildAtomicGroups` evidence_id 分组

**文件**：`internal/agent_gateway/prompt_atomic.go`

新增第二遍半 pass：把**未被 tool_call 组占用**且共享 `evidence_id` 的消息绑为 `evidence:<eid>` 原子组。单条引用不成组（交给 singleton），tool_call 组优先。

**为什么**：同一证据被 prosecutor 提出 → defender 反驳 → judge 评估时共享 `evidence_id` 但无 `tool_call_id`，此前各自独立，可被贪心打包分别丢弃 → 证据链断裂 → LLM 看不到原始证据内容。

### PR-2 (P1): 死配置激活 + token 预算单位

#### #2 `ScoreThreshold` 从死配置变活

**文件**：`internal/agent_gateway/prompt_greedy.go` + `prompt_compressor.go`

`GreedyPack` 新增 `scoreThreshold float64` 入参，排序后、贪心循环前预过滤低于阈值的组；`CompressScored` 传入 `cfg.ScoreThreshold`。

**为什么**：`AGENT_GATEWAY_SCORE_THRESHOLD` 此前只被写进 `CompressionInfo` 供日志，运维调它零效果 —— 违反"配置即代码"。

#### #5 字符数预算 → 内容感知 token 预算

**文件**：`internal/agent_gateway/prompt_greedy.go` + `prompt_atomic.go`

```go
// 新增：按字符类别加权的 token 估算
func EstimateTokens(text string) int {
    cjk, other := 0, 0
    for _, r := range text {
        if r >= 0x2E80 { cjk++ } else { other++ }
    }
    return cjk*3/2 + other/4
}
```

`AtomicGroup` 新增 `EstimatedTokens` 字段（`BuildAtomicGroups` 填充），`GreedyPack` 的 target 与 accum 全部改用 token；`tokens()` 访问器在 `EstimatedTokens == 0` 时回退 `GroupLength`（兼容手工构造的测试）。

> ⚠️ **对 ADR 原文方案的修正**：ADR 0044 §3.1 建议"加 token 估算（`chars / 3`）"。实施时发现**该方案无效** —— `chars / N` 与旧的字符数预算线性同构，GreedyPack 的 `accum + gTokens > target` 比较在等比例缩放下结果完全一致，不改变任何保留决策。真正的根因是"字符数不能反映 token 成本"，因此改为按字符类别加权。详见 ADR 0044 §3.3。

### PR-3 (P2): recency decay + 判决质量回环

#### #4 评分 recency decay

**文件**：`internal/agent_gateway/prompt_scorer.go`

`ScoreMessages` 末尾追加：

```go
const recencyAlpha = 0.3
if n := len(out); n > 1 {
    for i := range out {
        recencyWeight := float64(i) / float64(n-1)  // 0=最早, 1=最新
        out[i].Score = (1-recencyAlpha)*out[i].Score + recencyAlpha*recencyWeight
    }
}
```

**为什么**：旧公式位置信息只有首末各 +0.3，中间完全无位置信号。极端 budget 下"开场陈词"这类早期高分消息会挤掉近期关键推理。

**注意**：decay 是"混入"而非"覆盖"，首尾消息的 `position_boost` 仍体现在 final 上，故整条序列不保证严格单调（这是设计如此，测试按此断言）。分项字段（`RoleWeight` / `PositionBoost` / `ReferenceBoost` / `TypeBoost`）原样保留，供诊断与测试断言。

#### #7 判决质量回环指标

**新增文件**：`internal/courtroom/verdict_quality.go`（纯函数）+ `internal/observability/metrics.go`（常量）

```go
MetricVerdictEvidenceAccuracy = "verdict_evidence_accuracy"
```

`finishTrial` 在 verdict 落库后计算：判决书正文引用的证据 display id（`E001` 形式，兼容 `E1` / `E-001`）中，能在本次庭审证据列表里找到源头的比例。`<1.0` 说明压缩丢了证据链或 LLM 幻觉，同时打 `log.Printf` 便于定位。best-effort，不影响 verdict 落库。

**为什么放在 `finishTrial` 而不是 Gateway**：判决质量是 trial 级指标，不是 per-call 指标。

**§2.1 说明**：本项是**只读质量度量**，不参与判决计算、不改变任何权重或采纳结论，因此不属于 AGENTS.md §2.1 的裁决逻辑范畴。若将来要用该指标**反过来自动调整**压缩策略，则属 §2.1，需先讨论授权。

### PR-4 (P3): abstractive summary（opt-in）

**新增文件**：`internal/agent_gateway/summary_generator.go`

- 新 env 开关 `AGENT_GATEWAY_SMART_COMPRESSION_ABSTRACTIVE_SUMMARY`（**默认 false**，成本 opt-in）
- `SummaryGenerator` 接口 + `NewSummaryGenerator(client, model)` LLM 实现 + `BuildAbstractiveSummary` 编排
- 用**裸客户端**（Gateway 构造时的 `inner`）而非 Gateway 自身，避免 Gateway → compressor → Gateway 递归
- 低温（0.3）+ 短 `max_tokens`（400）+ 独立 15s 超时；输入按最近 20 条、单条截断 800 字符
- 任何失败（生成器 nil / 报错 / 返回空）自动回退 extractive `BuildEarlierSummary`

**为什么**：extractive 摘要只列 anchor（evidence_id + 角色 + 120 字 preview），LLM 看得到"被告已知情"这个结论却看不到依据，可能编造其他依据。

## ⚠️ 实施与验证中发现的三个额外问题

前两个同源（**字段搬运漏项**），都是 **dev compose 实跑才暴露的**——单元测试全绿也照样漏，因为单测直接构造 `GatewayConfig`，不经过 `main.go` 的手工映射。

### 问题 A（本次引入，已修）

`AGENT_GATEWAY_SMART_COMPRESSION_ABSTRACTIVE_SUMMARY` 在 `config.Load()` 里读到了，但 `cmd/server/main.go` 构造 `agent_gateway.GatewayConfig` 时**没有搬过去** → 压缩照跑、永远走 extractive，没有任何日志。属于"功能静默死亡"，不实跑根本发现不了。

### 问题 B（存量 bug，本次顺带修复 —— 请重点确认）

同一个手工映射里，**下面 9 个字段从未被搬运过**：

```
LLMTimeoutSec / CacheEnabled / CacheTTLSec / CacheMaxEntries
Breaker（整块 BreakerConfig）/ FileLoggerPrompts / FileLoggerPromptsMaxBytes
```

后果：**ADR 0013 的 Response Cache 与 Circuit Breaker 事实上从未在运行时生效**（`gateway.go` 里 `cfg.CacheEnabled` / `cfg.Breaker.Enabled` 恒为 `false`），ADR 0037 为它们加的 metric 恒为 0。v2.1 F5 "三个默认开关全开" 的叙述与实际不符。

之所以一直没被发现：本机 `.env` 恰好把 `CACHE_ENABLED` / `BREAKER_ENABLED` 都写成 `false`，与"永远 false"撞了巧合；一旦有人改成 `true` 就会被静默忽略。

**本机行为影响**：`.env` 里这两项都是 `false`，所以本次修复在当前 `.env` 下**不改变运行时行为**；只有当用户把 `AGENT_GATEWAY_CACHE_ENABLED` / `AGENT_GATEWAY_BREAKER_ENABLED` 改成 `true` 时才会真正启用（即"让旋钮开始起作用"）。如希望保持缓存/熔断永久关闭，把 `.env` 里那两项留 `false` 即可。

### 防复发

映射抽成 `buildGatewayConfig()`（`cmd/server/main.go`），并加反射测试 `TestBuildGatewayConfig_MapsEveryField`。新增 `GatewayConfig` 字段只需在 config 结构 + 映射函数各加一处，测试自动覆盖漏搬。

## 🔴 问题 C（存量 bug，严重，本次修复）：压缩器把 system prompt 截断成失忆

### 现象

`react_runner.go` 的 `buildInitialMessages` 把 baseRules + 工具说明 + 庭审历史拼成**一条 system 消息**（实测 12~14 KB），整个 `messages` 数组往往就只有这一条。而压缩器末尾的「单条超长截断」循环对 system 同样生效，用普通对话内容的 `3000 → 1500` 处理它。

来自 `backend/logs/agent_gateway_2026-09-21.log`（34 次压缩调用）：

| 指标 | 值 |
|---|---|
| 受影响调用 | **16 / 34** |
| 截断幅度 | `12304→1500` / `13883→1500` / `13331→1500`（**87~89% 被销毁**） |
| 后果 | 只剩前 1482 字节（baseRules 开头），**工具说明 + 全部庭审历史丢失** |

**连带观测**：同批日志有 4 条 `streamSpeakContent hallucination validation failed ... evidence_ref_empty_with_citation pattern="证据7,证据12"`（ADR 0015/0021 反幻觉校验打回）。模型失去庭审历史后不知道庭上有哪些证据，转而编造证据编号。（该告警在 gateway 关闭的对照组也出现过，故非唯一成因，但截断明显加剧。）

**代码自相矛盾**：同文件注释写着「system 消息始终强制保留」，但只保证不被**丢**，没保证不被**截断**。

**附带缺陷**：截断用裸 `Content[:keep]` 按字节切，system prompt 几乎全中文 → 切口落在字符中间，**产出非法 UTF-8** 塞进 LLM 请求。`agent.truncateForPrompt`（庭审历史逐行 240 字节）有同样问题。

### 修复

| 改动 | 内容 |
|---|---|
| system 独立上限 | `compressMaxSystemMsgLen=24000` / `compressSystemTargetLen=20000`（实测最大值 13883 的 1.7 倍）。**不做成无限**：system 含庭审历史，会随消息数增长 |
| rune 安全截断 | 新增 `cutBytesRuneSafe(s, n)` —— 字节预算语义不变，n 落在 rune 中间时回退到边界 |
| 消重 | 三处重复的截断循环合并为 `truncateOversizedMessages()`，保证三条路径对 system 处理一致（原 bug 正是三处都无条件截断） |
| `truncateForPrompt` | 同样改 rune 边界回退 |

### 验证

- **单元**：`prompt_compressor_test.go` +8、`react_runner_test.go` +2。**已实测**把 system 分支去掉后，三个 `*_SystemNotTruncated` 立即失败并报 `want 12000 bytes, got 1500 bytes` —— 与生产日志症状一致
- **eval baseline**：该 transcript 无消息超 3000 字节，A/B 实测本修复对其数字**完全无影响**（smart `3138 chars / kept 9` 前后一致）
- **⚠️ in-situ 复验未完成**：执行期间宿主 **D: 盘写满（652G/652G，剩 7.8M）**，Docker containerd 存储转只读，无法创建/启动容器。属环境故障。磁盘腾出后复验方式：开 gateway + 小 budget 跑一场，确认 FileLogger 里 `compression_before_count=1` 的 `react_think` 调用 `after_length` 不再为 1500

## 📌 dev compose 配置缺口（未改，仅记录，需用户决定）

`docker-compose.dev.yml` 的 backend 服务只显式传 `AGENT_GATEWAY_LLM_TIMEOUT_SEC`，其余 gateway 变量依赖根 `.env`；而根 `.env` **没有** `AGENT_GATEWAY_ENABLED`，其 Go 默认值为 `false`。

**结论：默认 `docker compose -f docker-compose.dev.yml up -d` 起来时，Agent Gateway 整体是关闭的**（`AGENT_GATEWAY_SMART_COMPRESSION=true` 等配置不起作用，压缩/预算/缓存/熔断都不跑）。

本次验证是通过临时容器注入 env 绕过的，**未修改 `.env`**（AGENTS.md §8 红线）。是否在 compose 里补默认值由用户决定。
